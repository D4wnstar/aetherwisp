Query optimization is the practice of optimizing a database query for some metric, typically to minimize the time of execution. Optimization is both a manual effort of the programmer and an automated effort of the [[database management system]], which calculates and stores data designed for the specific purpose of reducing redundant operations.

When a query is executed, it is passed through an **optimizer**, which is a component of the DBMS whose purpose is to optimize queries using metadata and statistical data by creating an **execution plan**. One simple statistic used is the number of records (rows) $N_\text{rec}$ in a table. The DBMS keeps track of the number of distinct values (keys) for each attribute (column). A high number of keys $N_\text{keys}$ with respect to the number of rows implies that the attribute is highly **selective**, meaning that a single value returns very few rows and is thus a good filter. Similarly, few keys means that it is not selective. The extreme cases are unique values (perfectly selective) and constants (completely non-selective). Other useful values are the minimum and maximum values for an attribute (if the data type has a defined order).

To understand optimization, it pays to have a better understanding of tables at a lower level. In a file system, a file is not stored in a monolithic fashion, but is rather split into fixed-size units called **pages** or **blocks**. The page size is chosen by the operating system. Since all persistent data is ultimately stored on disk, a database table is also stored as a collection of pages at the operating system level. The number of pages $N_\text{pages}$ is another statistic useful for optimization.

Persistent memory on disk is called **secondary memory**. **Primary memory** is instead a temporary buffer stored in RAM managed by a different component of the DBMS, the **buffer handler**. The RAM buffer is much faster but is of course ephemeral, and it is structured in the same way as regular files on disk in terms of page divisions. When a write query is executed, the DBMS fetches the pages in which the record is contained from secondary memory and copies them into the buffer. The operation is then carried out inside the buffer and, if successful, the end result is copied back into the appropriate table(s) in secondary memory. The query is considered completed only after this copy-back-to-disk is done. Thus, each write operation then requires two copy operations: one from secondary to primary memory and one from primary back to secondary. This is all unavoidable I/O operations that incur overhead, but the benefit of this model is that operations in primary memory are *fast*.

To fetch records out of pages we need to know where they are and how large they are. [[Pointer|Pointers]] to memory addresses are handled by the the DBMS, so we won't focus on them, but the size of each record is an interesting topic. In the simplest case, each record is a fixed size as determined by the data types of the attributes. For example, a row with containing exactly five [[computational number formats|int32]] numbers (each 4 bytes) would occupy 20 bytes of memory. Knowing that all records in a table have a fixed size makes a lot of memory operations much easier: for example, if a record is deleted, the DBMS knows that it can reuse this space when it inserts a new record, because it'll fit perfectly. This makes fixed-size records quite efficient in terms of computational cost. It also makes predicting the size of a table easy: just multiply $N_\text{rec}$ by the size of a single record.[^1] However, many data types have variable size, chiefly `VARCHAR` for variable size strings. Since these types conform to the smallest memory needed to store a value, they are quite efficient in terms of memory usage. In return, you lose all the convenient properties that a fixed size brings you, like drop-in replacement of records.

To go one step deeper, let's see how pages are organized inside of a file. You might expect them to be sequentially ordered in memory and to reconstruct the entire file you just read them all back-to-back. Well, you'd be right, as this is one file organization model called a **sequential file**. In a heap file, pages are a [[linked list]]. Each page contains a pointer to the next one. Pages are not in general stored next to each other in memory since you access them through pointers anyway. This model therefore removes the constraint of sequential memory allocation at the cost of having to store pointers and, more importantly, adding the need to following pointers over and over until you have the page you need. To ease this a bit, a pointer is also separately stored for the last page. In a heap file, the cost of query operations goes as follows:
- *Insertion*. The cost is constant. One operation is done to add a record to the last page (which we have a pointer for) and another to save the page to secondary memory.
- *Searching*. It's a linked list. To find something, you need to start at the first page and follow every single pointer until you get to the page that contains the record you're looking for. This can be *extremely* expensive; if the record is in the last page, you're stuck reading every single page before just to end up finding it at the very end. Assuming the record exists, the average number of operations is $N_\text{pages}/2$, but it can be as small as $1$ (the record is in the first page) or as high as $N_\text{pages}$ (the record is in the last page). Furthermore, if the record doesn't exists, the cost is a constant $N_\text{pages}$ (you scan everything just to not find it).
- *Updating* and *deleting* both inherit the cost of searching, since you first need to search for the record before modifying it.

[^1]: Plus the metadata related to the table, but that's tiny compared to the record memory for any table with enough records for you to care about this.
