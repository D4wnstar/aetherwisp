Query optimization is the practice of optimizing a database query for some metric, typically to minimize the time of execution. Optimization is both a manual effort of the programmer and an automated effort of the [[database management system]], which calculates and stores data designed for the specific purpose of reducing redundant operations.

When a query is executed, it is passed through an **optimizer**, which is a component of the DBMS whose purpose is to optimize queries using metadata and statistical data by creating an **execution plan**. One simple statistic used is the number of records (rows) $N_\text{rec}$ in a table. The DBMS keeps track of the number of distinct values (keys) for each attribute (column). A high number of keys $N_\text{keys}$ with respect to the number of rows implies that the attribute is highly **selective**, meaning that a single value returns very few rows and is thus a good filter. Similarly, few keys means that it is not selective. The extreme cases are unique values (perfectly selective) and constants (completely non-selective). Other useful values are the minimum and maximum values for an attribute (if the data type has a defined order).

To understand optimization, it pays to have a better understanding of tables at a lower level. In a file system, a file is not stored in a monolithic fashion, but is rather split into fixed-size units called **pages** or **blocks**. The page size is chosen by the operating system. Since all persistent data is ultimately stored on disk, a database table is also stored as a collection of pages at the operating system level. The number of pages $N_\text{pages}$ is another statistic useful for optimization.

Persistent memory on disk is called **secondary memory**. **Primary memory** is instead a temporary buffer stored in RAM managed by a different component of the DBMS, the **buffer handler**. The RAM buffer is much faster but is of course ephemeral, and it is structured in the same way as regular files on disk in terms of page divisions. When a write query is executed, the DBMS fetches the pages in which the record is contained from secondary memory and copies them into the buffer. The operation is then carried out inside the buffer and, if successful, the end result is copied back into the appropriate table(s) in secondary memory. The query is considered completed only after this copy-back-to-disk is done. Thus, each write operation then requires two copy operations: one from secondary to primary memory and one from primary back to secondary. This is all unavoidable I/O operations that incur overhead, but the benefit of this model is that operations in primary memory are *fast*.

To fetch records out of pages we need to know where they are and how large they are. [[Pointer|Pointers]] to memory addresses are handled by the the DBMS, so we won't focus on them, but the size of each record is an interesting topic. In the simplest case, each record is a fixed size as determined by the data types of the attributes. For example, a row with containing exactly five [[computational number formats|int32]] numbers (each 4 bytes) would occupy 20 bytes of memory. Knowing that all records in a table have a fixed size makes a lot of memory operations much easier: for example, if a record is deleted, the DBMS knows that it can reuse this space when it inserts a new record, because it'll fit perfectly. This makes fixed-size records quite efficient in terms of computational cost. It also makes predicting the size of a table easy: just multiply $N_\text{rec}$ by the size of a single record.[^1] However, many data types have variable size, chiefly `VARCHAR` for variable size strings. Since these types conform to the smallest memory needed to store a value, they are quite efficient in terms of memory usage. In return, you lose all the convenient properties that a fixed size brings you, like drop-in replacement of records.

To go one step deeper, let's see how pages are organized inside of a file. You might expect them to be sequentially ordered in memory and to reconstruct the entire file you just read them all back-to-back. Well, you'd be right, as this is one file organization model called a **sequential file**. However, it's not the only such model: the **heap file** and the **hash file** are two other valid models for page organization. Let's see them in more detail. %%TODO: Check if this is wrong%%

Pages are a [[linked list]]. Each page contains a pointer to the next one. Pages are not in general stored next to each other in memory since you access them through pointers anyway. This model removes the constraint of sequential memory allocation at the cost of having to store pointers and, more importantly, adding the need to follow pointers over and over until you have the page you need. To ease this a bit, a pointer is also separately stored for the last page.

In a heap file, records are unordered: they are all thrown disorderly on a big heap. In this file model, the cost of query operations goes as follows:
- *Insertion*. The cost is a constant two operations. One operation is done to add a record to the last page (which we have a pointer for) and another to save the page to secondary memory.
- *Searching*. It's a linked list with no internal ordering. To find something, you need to start at the first page and read every single page until you get to the one that contains the record you're looking for. This can be *extremely* expensive; if the record is in the last page, you're stuck reading every single page before just to end up finding it at the very end. Assuming the record exists, the average number of operations is $N_\text{pages}/2$, but it can be as small as $1$ (the record is in the first page) or as high as $N_\text{pages}$ (the record is in the last page). Furthermore, if the record doesn't exists, the cost is a constant $N_\text{pages}$ (you scan everything just to not find it). If you instead search for an interval, you always need to do a full scan because the lack of ordering means that there is no interval on disk. The cost is guaranteed to be $N_\text{pages}$.
- *Updating* and *deleting* both inherit the cost of searching, since you first need to search for the record before modifying it. The cost is one search, plus one operation.

In a sequential file, records are ordered according to an attribute. The cost of query operations goes as follows:
- *Searching*. By taking advantage of the ordering, we can take advantage of algorithms to search on an ordered list. These algorithms generally have logarithmic complexity $O(\log_{2}N_\text{pages})$, so the average search cost is much lower than the linear complexity of a heap file. When searching for an interval, because of ordering, we know that the upper bound always comes after the lower bound, so the cost is a regular search, plus the cost of reading all subsequent pages until you find the upper bound. To estimate the latter cost, we can define a **selectivity factor** $f_{s}\in[0,1]$ to represent how uncommon the key we're searching for is. The rarer it is, the smaller the interval is on average. An a rough estimate, the cost of reading all interval pages is $f_{s}\cdot N_\text{pages}$.
- *Inserting*. When inserting, ordering is actually a pretty big problem. Because you need to maintain ordering, you need to insert a record specifically where it should be in the order; you can't just append it like you would on a heap file. First, you need to search for the place to insert in. Then, you check if there is space left in the page. If there is, that's the best case scenario. You add the record and you write the page back to disk: that's $\log_{2}N_\text{pages}+1$ operations on average. If there's no space left, you have a problem. You can't just insert somewhere (need to maintain ordering), so you need to make space. There's a variety of algorithms to handle sequential insertions, so the exact details are implementation-dependent, but the idea is that you need to evict *something* from the current page. As a simple example, say you remove the last element of this page. Now you can add the new one, but you need to put the one you just removed somewhere. Due to ordering, it must become the first element of the next page. But if *that* page is full, you have the same problem. In fact, you'll have this problem for *every* page thereafter until you find one that's not full. A sequential insertion then causes a cascade effect where you may have to modify every single page after the one you're inserting into, which can get quite expensive in terms of operations (the exact cost depends on the algorithm).
- *Updating* and *deleting* both inherit the cost of searching and don't have issues with ordering, so they are relatively cheap. Deleting in particular doesn't have the space issues of insertion since you're freeing space instead of filling it. The cost is one search, plus one operation.

In a hash file, each page has a **hash** value calculated for it. The hash is a unique identifier that's fast to calculate; it is never stored on disk. Then, a function $H:A\to \{ h_{1},\ldots,h_{k} \}$ can be applied on a record (specifically, on an attribute $a\in A$) to calculate the hash $h_{i}$ of the corresponding page $i$ where the record is stored.

[^1]: Plus the metadata related to the table, but that's tiny compared to the record memory for any table with enough records for you to care about this.
