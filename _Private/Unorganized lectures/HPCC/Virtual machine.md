A **virtual machine** (**VM**) is an emulated [[operating system]], called the **guest OS**, running inside of a real operating system, called the **host OS**. The VM is said to be **virtualized**. A VM works by emulating the hardware model through software. The program that manages virtual machines is called a **hypervisor** (or **virtual machine monitor**).

For a hypervisor to be useful, it must handle VMs in a way that satisfies (or rather, balances) three properties: equivalence, safety and performance. Equivalence means that the VM behaves identically to a real OS, and any code running in the VM can't tell it's on a VM. Safety means that errors in the VM do not propagate outside of it, so that even if the guest OS crashes, the host OS is safe. Performance means that the VM executes code with comparable performance to a real machine. Satisfying all three properties at once is not easy, as they are interrelated. For instance, safety can be guaranteed by having the host OS inspect every single virtual CPU instruction, but this is terrible for performance. Meanwhile, if the VM runs directly in kernel mode on the real CPU, this allows maximum performance but is extremely unsafe.

However, this model only works if the hardware always cooperates. This is not always true. To understand why, notice that trap-and-emulate relies on one assumption: every instruction that matters for virtualization must trap when attempted in user mode. Such an instruction is said to be *privileged*, it executes only in kernel mode and traps otherwise. But the privilege of an instruction is not a semantic fact, you can't decide it in code or software. It's decided by the ISA of the CPU and therefore the physical structure of the silicon in the processor. It's a hardware fact chosen at manufacturing and something you simply accept as an end user, as you can't realistically do anything about it. This is a problem because whether an operation is privileged or not does not necessarily have an impact on whether it's *sensitive* or not, in the sense of whether it should be checked by the hypervisor. In the ideal case, all sensitive operations are privileged and all regular (non-sensitive) operations are unprivileged. But you can't guarantee this is true: one good example is the `popf` (pop flags) call on x86, which pops a word from the top of the stack into the `EFLAGS` register. Most flags in EFLAGS are harmless, handling arithmetic operation like the sign of a number. But *some* flags are dangerous: namely, the `IF` flag manages the interrupt enable bit, which is *extremely* privileged. So this is a case where an operation is considered okay at the hardware level, but not okay at the semantic level. Operations like these make hypervisor construction really difficult, because they break the idea that hardware *always* knows when an operation is dangerous and therefore can be relied upon for safety. This is known as the **Popek-Goldberg theorem**. It states that a trap-and-emulate hypervisor can only be constructed if and only if all sensitive operations are privileged. This is not true in general and is architecture-dependent, so what do we do? Well, it's complicated, but over time, three different approached emerged.

One, use software to fix bad instructions on non-Popek-Goldberg-compliant architectures like x86. This is known as **binary translation**, but because it involves software and constant checking, it's slow and complicated. Two, break complete isolation and have the VM be aware that it's a VM. Then, the VM can use special **hypercalls** to handle sensitive operations. This is known as **paravirtualization**. This is fast and avoids the complexity of binary translation, but requires modifying the source code to work on a VM specifically, which more often than not isn't feasible for third-party software. Three, improve the hardware and introduce **hardware-assisted virtualization**. Better hardware can have more modes designed for hypervisor use specifically. This provides better support for trap triggers to make sure that sensitive instructions do indeed trigger hypervisor control directly at the hardware level. Real implementations include Intel VT-x and AMD-V. Hardware-assisted virtualization is the current dominant paradigm because it's widely available on common hardware and has the best performance of all three, while still guaranteeing safety.
## History
Virtualization came up as an idea originally because of inefficient CPU utilization. Without virtualization, a single machine (server, to be specific) can only be used for one application. If the application is single-[[Thread (computer science)|threaded]], on modern CPUs it would use maybe 10-15% of the CPU at peak. This is a very inefficient use of hardware, and yet it forces developers to have separate hardware for each application. It's expensive, inefficient and requires lots of space and cooling. Of course, [[parallel programming]] can improve CPU usage and that's the way to go for single, expensive application: this way you move into HPC territory. But that's not always feasible or even reasonable: sometimes you just have multiple single-threaded applications. If that's the case, we'd need a way to isolate each application so that they take their own core(s), but don't "see" each other. The solution is virtualization: emulate the entire [[operating system]] and make the application run in the emulator, this way it will "think" it's on a separate machine, but in practice there can be multiple virtual machines on the same physical machine (hardware). Assuming the emulator is faithful to the OS and sufficiently fast (a big assumption!), this solves the "multiple apps, single hardware" problem.
